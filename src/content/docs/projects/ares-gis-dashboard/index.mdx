## What the platform does

The dashboard is built to support real-time situational awareness and operational decision-making for ARES Duval during activations. It pulls many sources into one operational view of Duval County, and it is designed to complement Net Control operations by making it easier to see resources, spot gaps and coordinate activity in a fast-moving environment.

**One operational picture of Duval County:**

- JFRD fire stations, law enforcement, hospitals and shelter locations, using official City of Jacksonville ERAT (Emergency Response) map services where they are available. If the live ERAT service is unreachable, the map falls back to locally stored, validated points.
- Flood zones, weather alerts and other hazard overlays.
- ARES and SKYWARN frequency references and repeater locations, for operators' quick reference. (Specific frequencies are not reproduced on this website.)
- Live and fallback data integration with a priority-based system, so the picture stays usable if external feeds fail.

**A lightweight command tool, not only a map:**

- **Operational Status Layer:** operators can mark facilities as Available, Monitoring or Unavailable, and each change is timestamped.
- **Action-driven interface:** quick access to zoom, directions and tasking workflows from any map feature.
- **Offline-aware design:** cached data and low-bandwidth usability for degraded communications.

The project is still a work in progress. A future step is plugging in an operator roster with call signs, which would only be done with the group's approval and with contact details kept off any public view.

## Goal

Give a net control station or command post one map that shows where ARES operators are, what incidents and tasks are open, and who is assigned to what, no matter which radio system each operator is reporting through.

"Done" means a dashboard that:

- keeps working when some feeds are down,
- tells you honestly which feeds and providers are healthy,
- lets a dispatcher find the nearest available operator and assign them in a few clicks, and
- keeps the incident's communications plan, message traffic and activity log next to the map.

## Constraints

- **Mixed sources:** operators report by APRS, Meshtastic mesh, DMR or a manual check-in, and one person may show up on more than one of them.
- **Degraded networks:** upstream feeds (NOAA/NWS, FEMA, FL511, statewide outages, ArcGIS) may be unreachable during an incident. Every feed reports its own state, such as live, cached, fallback or offline, instead of failing silently.
- **Validated base data first:** the map always starts from locally stored, validated GeoJSON layers, and live layers are added on top when they respond.
- **Security:** every page and API route except the health checks requires a login. Every write also requires an admin token, and all credentials live in the host's secret settings, never in the repository.
- **Privacy:** sharing your own GPS position is opt-in, off by default, and expires automatically when your browser stops sending updates.
- **Persistence on a cloud host:** state is plain JSON, so on Render it must live on a mounted persistent disk. The diagnostics panel warns when it doesn't.

## Architecture

```text
APRS (aprs.fi API) ──────┐
Meshtastic (MQTT / API) ─┤                        ┌─► Operator board (filter by source and status)
DMR tracker (optional) ──┼─► Tracking fusion ─────┼─► Map markers (styled by best source, source count)
Manual check-ins ────────┤   (merge by call sign, └─► Nearest-operator dispatch
Browser GPS shares ──────┘    alias or node ID)

Incidents · Tasks · Assignments · Check-ins ─► JSON store (APP_DATA_ROOT) ─► Express API ─► Leaflet UI
NOAA / NWS · FEMA · FL511 · statewide outages · SKYWARN ─► feed cache ─► feed status and overlays
Validated local GeoJSON + official ArcGIS / HIFLD layers ─► layer service ─► Layers drawer and map
```

### Tracking fusion

- Merges APRS, Meshtastic, DMR, manual check-ins and opt-in browser GPS shares for the same operator. It matches on call sign, APRS call sign, Meshtastic node ID or DMR ID.
- Meshtastic nodes whose long or short name contains a ham-style call sign are matched to that operator.
- Each merged marker shows a source count and badges, and is styled by its best current source.
- Positions older than the stale threshold (6 hours by default) are marked stale.
- Refreshes run as one unified cycle and report partial success, so one failing provider doesn't blank the others.
- Fused reads are recalculated from the current raw operator records. An earlier cached version made new assignments look unsaved.

### Dispatch and the assignment lifecycle

- **Nearest operators:** for any incident, the dashboard ranks operators by straight-line distance in miles. It also shows how long ago each one last checked in and whether they are eligible for dispatch. Operators who are available, monitoring, en route or on scene are eligible. Anyone offline, unavailable or already assigned to another incident is not.
- **Assignments:** dispatch writes the assignment to the operator record first, then refreshes tracking so every view updates quickly. Each assignment is logged as an event and drawn on the map as a line from the operator to the incident.
- **Lifecycle:** operators move through statuses such as available, assigned, en route, on scene, needs relief and released. Inline controls reassign or release an operator without leaving a stale incident link behind.

### Incident workspace (ICS-style)

Each incident carries more than a map pin:

| Area | Fields |
| --- | --- |
| Incident record | Title, type, status (default "monitoring"), priority (high for active incidents, otherwise medium), location |
| Workspace | Operational period, incident commander, net control, primary and tactical channel, staging location, objectives, situation report |
| Communications plan | Assignment, function, channel, tone, mode, operator, notes, status (planned by default), primary flag |
| Message log | From, to, precedence (routine by default), subject, body, status, reply expected, sent via |
| Activity log | Author, activity, resource, location, operational period |

The communications plan, message log and activity log can each be added to, edited and deleted from the dashboard.

### Security and reliability (v8)

- Timing-safe comparison for the login password and the admin write token.
- Production will not start with auth off while default credentials are in use.
- Security headers: nosniff, frame and referrer policy, and a permissions policy limited to geolocation and Web Serial. `X-Powered-By` is removed and CORS is off by default.
- Timeouts on every outside data call. The FL511 camera proxy refuses redirects.
- Crash-safe data file writes, graceful shutdown, and no internal error details sent to browsers.
- The ICS-309 CSV export neutralizes spreadsheet formula injection. User text in popups, the net log and printed forms is HTML-escaped.
- `npm audit` reported 0 vulnerabilities at release.

**Known follow-ups:** no Content-Security-Policy yet, the admin token is held in browser storage, and basic auth has no rate limiting.

## Configuration

Configuration is environment-driven. The repository ships an example file with placeholder values only.

- **Security:** basic authentication on, a non-default username and password set in the host dashboard, and a generated admin API token.
- **Persistence:** the app data root points at the Render disk mount, so operators, incidents, tasks and check-ins survive restarts and redeploys.
- **Tracking:** tracking on, with a 20-second render interval and a 6-hour stale threshold.
- **Providers:** APRS, Meshtastic and DMR are each off by default and are turned on only after their credentials and endpoints are configured. APRS polling uses caching, batch limits and a rate-limit backoff.
- **GPS:** server-side serial GPS is for local Windows use only. Cloud deployments leave it off and use the browser's Connect GPS button instead.
- **GPS sharing:** on, with a 2-minute expiry.

Operational settings such as tracked call sign lists, mesh channel settings, radio channel plans and access credentials are deliberately left off this page.

## Build steps

1. `npm ci`. The install also builds the browser bundles.
2. `npm start`, then open the dashboard locally.
3. Optional: `npm run seed:data` for sample data. This overwrites the local data folder.
4. For hosting, create a Render Blueprint from the repository, set the secret values Render asks for, and deploy. The health check path is `/healthz`.

## Safety notes

- This is a situational awareness tool, not a dispatch system of record. Follow the served agency's procedures.
- Position data is only as current as each source. Stale positions are marked, and a position should never be treated as confirmed without a radio check.
- Keep the dashboard behind authentication. Operator positions are sensitive during an incident.

## Lessons learned

- Fused tracking has to recalculate from the current raw operator records. Returning a cached operator view made dispatch assignments look like they had not saved.
- An auth layer that quietly leaves routes open when settings are missing is worse than no auth layer. The middleware now rejects unauthenticated requests even when the auth settings were left out.
- Showing each feed's health on screen matters more than adding another feed.
- A failing test suite is not always a failing app. Read the first error before fixing code. Here, the browser had simply never been installed.
- Running UI tests against the live data folder had quietly shipped about 480 test records. Tests now run on a throwaway copy.
- Map-tile visual tests are only meaningful where real tiles load, so they are now opt-in instead of failing every offline run.
