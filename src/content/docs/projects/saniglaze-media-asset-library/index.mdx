## Overview

The Franchise Media Asset Library & Distribution Platform was an internal, browser-based application that gave SaniGLAZE International franchise members self-service search and access to corporate marketing assets kept in the company's HubSpot file store. It added tools for creating before-and-after images, assembling client-specific media packages, and maintaining the library itself.

I built it in 2026 as Vice President of Marketing at SaniGLAZE International, and it was used by the company's franchise network nationwide.

The application was built around the company's existing content system rather than beside it. Media files stayed where the corporate team already kept them, and the application retrieved them on demand through an authenticated API integration. That one decision shaped the rest of the design: franchise members got a single place to find and prepare approved materials, and the corporate team kept a single library to maintain.

I designed and built this application in 2026 while serving as Vice President of Marketing at SaniGLAZE International. ## 2. The Problem

SaniGLAZE's marketing collateral lived in the corporate HubSpot file store. That collection covered videos, sales brochures, technical data sheets, safety data sheets (SDS), before-and-after photographs, and other marketing materials. Franchise members needed these materials to market and sell in their own territories, and the corporate team needed to keep the collection organized.

The application was designed to address four points of friction.

### Locating assets

Franchise members needed a simple, browser-based way to find the right brochure, data sheet, SDS, video, or photo without relying on the corporate team to locate it for them. A library is only useful to a distributed network if the people in the field can find what is in it.

### Avoiding a second library

The obvious alternative, copying the collateral into a separate portal, would create a duplicate repository that had to be kept in step with the corporate original. Every new upload, replacement, or rename would have to happen twice, and any gap between the two copies would put outdated material in front of franchise members.

### Preparing materials for a client

Franchise members needed to present before-and-after results and assemble the right set of documents for a specific client. Both tasks are slow when every file has to be found, downloaded, and combined by hand.

### Maintaining the collection

Corporate personnel needed practical tools to find duplicate files and correct file names in the shared store, so that the library franchise members searched stayed clean and consistent.

### Who felt the friction

| User group | What they needed | What the application was designed to provide |
| --- | --- | --- |
| Franchise members | Fast, self-service access to approved collateral, plus ways to prepare it for a specific client | Searchable library, on-demand access, before-and-after images, client packages |
| Corporate marketing personnel | A way to serve the network without a second library to maintain | Self-service access built on the existing corporate file store |
| Authorized administrators | Tools to keep the shared store organized | Duplicate-file identification and remote file renaming |

## 3. What I Built

I built a hosted web application that acted as a search and access layer in front of SaniGLAZE's existing HubSpot file store.

Franchise members opened the application in a browser, searched or browsed an indexed catalog of corporate media, and opened or downloaded the assets they needed. The application retrieved each asset from HubSpot through an authenticated API integration rather than serving it from a separate copy, so HubSpot remained the single source of truth for the media files themselves.

On top of that library, I built two sets of tools:

- **Franchise tools** let members combine two photographs into a single before-and-after image and assemble a client-specific collection of assets for download as a package.
- **Administrative tools** let authorized corporate personnel identify duplicate files and rename files in the HubSpot file store directly from the application.

The result was one place where franchise members could find, prepare, and take away approved marketing materials, and where the corporate team could maintain the library those materials came from.

### How it fit into the existing business environment

- **HubSpot stayed the content system.** The application did not replace it, migrate away from it, or compete with it. It made the existing store easier to use for people outside the corporate office.
- **Corporate kept control of the source.** Because files were never copied into the application as a second library, the corporate team's existing store remained the place where the official version of each asset lived.
- **Changes landed in one place.** When authorized staff renamed a file through the application, the change applied to the file in the corporate store, so everyone working from that store saw the same corrected name.
- **The browser was the only requirement for franchise members.** Access did not depend on installing software or learning the corporate content system.

## 4. User Workflows

### Franchise member workflow

1. **Search or browse.** Find assets in the indexed library by searching or browsing the collection.
2. **Open on demand.** The application retrieves the selected asset from the corporate HubSpot file store when it is requested.
3. **Prepare it for use.** Depending on the task, either:
   - **Create a before-and-after image** by selecting two source photographs and generating one combined image, or
   - **Build a client package** by collecting the assets a specific client needs and downloading them together as a package.

### Corporate and administrator workflow

1. **Review the library** through the application.
2. **Identify duplicates** by filtering or flagging duplicate files for human review.
3. **Rename remotely** by correcting a file's name in the HubSpot file store from inside the application.
4. **Keep one corrected original.** The rename applies to the corporate file itself rather than to a local copy.

## 6. Architecture and Technical Highlights

The architecture is documented at the level the available evidence supports. Where a detail is unknown, this page describes the pattern and says so, rather than naming a technology.

### Architectural pattern

The application was a **search and access layer over an existing corporate content system**. Users worked in a browser; the application ran on a hosted server; the media lived in the corporate HubSpot file store and was reached through an authenticated API.

### Layer-by-layer view

| Layer | What is established | What is not documented |
| --- | --- | --- |
| Application interface | Browser-based; used by franchise members, corporate personnel, and administrators | Framework, page design, screen layouts |
| Application server | Ran on a hosted server | Language, backend framework, hosting provider |
| API integration | Authenticated API integration with the corporate HubSpot file store, used to retrieve assets and to rename files | Integration library, authentication method, endpoints, configuration (intentionally excluded) |
| Authentication and authorization | Administrative functions were for authorized corporate personnel and administrators | How users signed in and how roles were enforced |
| Data storage and persistence | Media files were not stored as a separate, persistent copy in the application | Whether a database or persistent metadata index existed; any caching |
| File handling and processing | Combined two images into one before-and-after image; assembled selected assets into a downloadable package | Image-processing method, output formats, archive format |
| Background jobs or automation | None documented | Whether indexing or other work ran on a schedule |
| Hosting and deployment | Hosted server | Provider, deployment process, environments |
| Security boundaries | Internal application, not publicly accessible; credentials and configuration are kept out of this case study | Specific controls in the original code |
| Error handling and reliability | None documented | Logging, monitoring, testing, error handling |

### Technical highlights

- **A layer over an existing platform.** The application was built around SaniGLAZE's HubSpot environment. It did not replace HubSpot or create a competing content system.
- **The source system kept the media.** Media files stayed in the corporate HubSpot file store and were retrieved on demand. This kept one authoritative library and avoided maintaining a duplicate media repository.
- **Read and write paths.** Most users read from the library through search, browsing, and downloads. Administrative renaming wrote changes back to the HubSpot file store, so a correction applied to the corporate original rather than to a local copy.
- **Separated audiences.** Franchise-facing features (search, before-and-after images, packages) were distinct from maintenance features (duplicate identification, renaming), which were intended for authorized corporate personnel and administrators.
- **Generated outputs from approved inputs.** Before-and-after images and client packages were built from assets already in the approved corporate library.
- **Confidential details excluded.** The HubSpot integration is described by its business function only. Authentication methods, credentials, endpoints, and configuration are intentionally left out.

## 7. Design Principles

<Callout type="lesson" title="Build around the system of record, not beside it">
The corporate HubSpot file store was already where the official assets lived. Building a layer in front of it, instead of a new library next to it, avoided the ongoing work and risk of keeping two copies in step.
</Callout>

<Callout type="lesson" title="Make self-service the easy path">
If finding an approved asset is faster than asking for one, people use the approved asset. The searchable library put the corporate collection within reach of every franchise member with a browser.
</Callout>

<Callout type="lesson" title="Fix data where it lives">
Remote renaming applied corrections to the corporate file itself. A fix made once was a fix for everyone using the store.
</Callout>

<Callout type="lesson" title="Give the field tools, keep governance central">
Franchise members got creation tools (before-and-after images, client packages), while maintenance tools (duplicate identification, renaming) were reserved for authorized corporate staff.
</Callout>

<Callout type="lesson" title="Support decisions, don't automate them away">
Duplicate handling was built to identify and filter duplicates for people to review, not to delete files automatically.
</Callout>
