## One-line summary

A local, offline Windows app that turns the [F-150 emergency-lighting upfit](/projects/f150-upfit/) into one checked config file, and lets me run the Whelen control head, the wiring and the bench test on screen before a single wire goes into the truck.

## Why I built it

The F-150 build had grown to 20 products, 18 circuits, 32 of the CanTrol's 40 outputs and a three-position slide plan, spread across a 98-page project document, a parts list and a wiring sheet. Every change (a new rear light, a relay moved to a different output, a re-labelled key) had to be retyped in three places, and the copies drifted. I wanted one source of truth that would:

- check the 12V design every time it changes (voltage drop, fuse against wire, total load against the module's rating),
- show exactly which light does what in each slide position and button, steady or flashed,
- keep every unconfirmed value visibly blank instead of quietly filling in a guess,
- and keep this portfolio's output plan current without hand-editing it.

## What it is

Upfit Studio (package name `upfit-kit`) is a Python application with two front ends on one engine:

- **Upfit Studio**, the main app: a modern interface in a native Windows window (Microsoft Edge WebView2 through pywebview). The page is a local file. There is no web server, and the page's content security policy blocks every network connection.
- **Classic app**: a standard-library Tkinter window with the same engine, which opens automatically if WebView2 can't start.
- **Command line**: `validate`, `build`, `diff` and `bench` for scripted checks. `validate` and `build` exit with an error code when the design has an ERROR finding, so they can gate a release.

The build lives in one file, `config/upfit.yaml`. The app reads it, checks it and writes it back only when I press Save, with a timestamped backup first and the file's comments and layout kept.

## Whelen Command CANport setup

New on 31 Oct 2026 (versions 0.8.0 to 0.8.10). The Whelen CanTrol can take up to eight vehicle signals from the truck's OBD-II port through the **Whelen Carbide CanTrol OBDII CANport Kit (CC5K1 - Ford)**, which I bought on 21 Oct and which arrived on 26 Oct. In Whelen Command you pick each signal from the list Command shows for the vehicle, then decide what it does: turn on a key's lights, run the brake pop, or switch something off. I planned all eight in Upfit Studio first, keyed them into my Command file, and then used Studio to check that the two agree.

Why it matters for this truck: the brake pop, the rear work light in reverse, the scene light when a door opens, and the "don't drive off with the take-downs on" rule all come from signals the truck already sends. None of them need a tap into factory wiring.

### The eight CAN inputs

This table is generated from the app's data, so it always matches the current plan. The same table appears on the F-150 [CanTrol output plan](/projects/f150-upfit/cantrol-output-plan/#canport-vehicle-inputs).

<UpfitStudioPlan show="canport" />

In plain terms:

- **Brake pedal (CAN 1)** runs the Option A brake pop: three outputs flash about 2 seconds, then the rear Z-6 heads burn steady red while the pedal is held. My Command file has the first pass only (LED Output 13 steady). The 2-second flash still needs a timer in Command.
- **Reverse (CAN 2)** turns on the Putco Work Blade's white rear flood (J1 Output 8), the same as the REAR FLOOD key.
- **Any rear door (CAN 3) or either front door (CAN 5)** turns on SCENE: the UBL Color Flood 2.0 burns steady white for loading gear.
- **Hazard switch (CAN 4)** turns on both arrows (FLASH) and turns them off with the hazards. The E68Xtreme sweep part of the arrows isn't set until the bench test.
- **Shifting out of Park (CAN 6)** switches the arrows off once. I can press them on again in Drive. This is the one input not yet programmed in Command, and it must be a one-time turn-off, not a lockout.
- **Parking brake (CAN 7)** turns TAKE DOWN on while it is set and off when it is released.
- **Shifting into Drive (CAN 8)** switches SCENE and TAKE DOWN off once, so I don't drive away with the white lights on. They can be pressed on again.

### Compare with a Whelen Command file (read-only)

Whelen Command saves the CanTrol's setup as a `.wln` file. Whelen doesn't publish that format. From two files I saved from Command 2.4.8.0 on 31 Oct, the app reads only the table of names inside (inputs, CAN signals, outputs) and the Command version, then lists the CAN signals in the file next to the plan's.

- Against my programmed file "-3", all eight signal names match the plan.
- Only the names are compared. Which output each signal drives, patterns and priorities are binary values the app does not decode, so I check those in Command by hand.
- The app **never writes** a `.wln` file. A wrong byte could load a bad setup into the controller that runs the warning lights and siren.
- The format notes are worked out from my own sample files and are marked UNVERIFIED in the code. A regression test checks the programmed file against the plan.

## Key capabilities

**Design**
- One YAML file for the whole build: vehicle, parts (with status), circuits, wires (color, function, where each lands), and the CanTrol control plan for slide positions 1 to 3, every key and the brake pop.
- Full product names everywhere. A check flags ruled-out short forms (for example "SpeedTurtle" or "STL") as errors so reports stay consistent with the project document.
- Wiring map, output board and control head views all read the same data.

**Electrical checks**
- Voltage drop over feed plus ground return, against 3% (critical) or 10% (non-critical). A blank ground length is assumed equal to the feed and flagged.
- ERROR if a fuse or CanTrol per-output limit exceeds the wire's ampacity; WARN if a fuse is under 1.25x continuous load.
- ERROR if the everything-on draw of CanTrol-fed circuits exceeds the module's 40 A total output rating (Whelen guide 14580G, p.3).
- ERROR if the plan would burn a flash-only product steady (set on the E68Xtreme stick from the Strobes N' More guide).
- Suggests the smallest standard fuse and thinnest wire that pass both checks.

**Simulation**
- Control head replica: 21 keys with my printed caps, 4-position slide (far left is off), slide LEDs, 7-dot arrow indicator, simulated siren keys, a hold-to-press brake pedal and a night backlight view. Priority order: brake pop, TAKE DOWN, WHITE, STEADY, slide.
- Each output is shown as steady (Turn On) or CanTrol Flash A/B.
- Test lab runs every combination and lists wiring gaps and suggested fixes, each of which asks before it saves.

**Vehicle inputs (CANport)**
- Plans up to eight Whelen Command CAN signal commands from Command's own list for the truck, with checks on slot, name, duplicates and action.
- Simulates each signal, including one-time turn-offs (Park ends, Drive starts).
- Compares the plan with a Whelen Command `.wln` file, read-only.

**Records and publishing**
- Every save writes a timestamped backup; Change history compares and restores them.
- Sync logs every save and can commit it to the private project repo, to this site and to a plain folder. Before each push it pulls with rebase so a change made elsewhere never blocks the next save; a real conflict stops before the push.
- The site copy leaves out notes, order numbers, tracking numbers and prices.
- Installer packet ZIP for a shop or EVT quote, with the Whelen Command programming sheet.

## How it feeds this site

Since version 0.5.0, each save writes `src/data/f150-upfit/upfit-studio.json` into this site's repository and commits it. When that reaches GitHub, Cloudflare Pages rebuilds the site. The [CanTrol output plan](/projects/f150-upfit/cantrol-output-plan/) and its [control head key map](/projects/f150-upfit/cantrol-output-plan/#control-head-keys) are generated from that file, so the published plan matches the app. The first sync landed on 31 Oct 2026 (see the [build log](/log/2026-10-31-upfit-studio-sync/)).

## Architecture (pattern level)

| Layer | What it does |
| --- | --- |
| `config/upfit.yaml` | The build: parts, circuits, wires, control plan, head key labels |
| Engine | Model loading, validator, electrical math, wiring map and plan simulator, test lab, bench session, diff, report and harness generation, head mount generator |
| Back end | A single API object exposed to the page through pywebview; only a fixed list of methods is reachable |
| Front end | One local HTML page (no network allowed by its content security policy) |
| Fallback | Tkinter classic app on the same engine |
| Sync | Local git commits; pushes only where switched on, with the user's own sign-in |

## Testing and verification

- **Done:** the pytest suite passes on Linux (195 pass, 6 skipped on version 0.8.10, Python 3.13, cloud container, 31 Oct 2026). New tests since 0.5.2 cover the CANport rules, the Command file reader against my programmed file, the sweep, the installer packet, reserved Windows file names and the build script. The change log records every Studio screen being driven in Chromium with no page errors (0.4.0 and 0.5.0), and I re-checked all 18 screens with no page errors while taking the screenshots above.
- **On Windows:** the change log shows the app being pulled and built on my Toughbook (0.8.1 fixed a Windows-only file name problem found there, and 0.8.2 fixed which config a rebuild ships). I have not recorded a full run of every screen in WebView2 on the Toughbook, so this page doesn't claim one.
- **Nothing electrical is tested.** The control plan is not bench-tested or programmed into the CanTrol, and CanTrol pin numbers come from Whelen guide 14580G without being proven on the module.

## Privacy

No network, no telemetry, no accounts. The app writes only when a button is pressed. The public data file excludes notes, order numbers, tracking numbers and prices; including prices is an opt-in setting that is off.

## Lessons learned

- Keeping blanks blank works: 131 open items is an honest picture of what still needs a measurement or a source, and it is much more useful than a filled-in sheet I can't trust.
- The first simulator showed every lit output as plain "on", which made a correct plan look like it burned the E68Xtreme steady. Showing steady vs flash per output fixed a display problem that looked like a design problem.
- Publishing from the same file as the app removes a whole class of drift between the build plan and the portfolio.
